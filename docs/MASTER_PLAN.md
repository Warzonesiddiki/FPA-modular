### Market check (Oct 2026)
Competitors (Anaplan, Pigment, Datarails, Cube, Vena, Planful) are cloud, per-seat ($1.5k–$30k+/yr), Excel-add-in or implementation-heavy ([1](https://getaleph.com/answers/ai-fpa-software-variance-detection), [2](https://financecopilothq.com/best-fpa-software/)). The 2026 differentiators are: AI variance commentary with drill-down to transaction, anomaly detection, agentic forecasting ([3](https://getaleph.com/answers/best-ai-fpa-tools)). **Our wedge:** the same AI-assisted month-end, but offline, local-only, one-time desktop tool for a single analyst at a mid-size company — no seats, no cloud data exposure, no 8–16-week implementation. AI drafts words around verified numbers; it never computes a number.

## 2. Product definition

### 2.1 The job (the monthly rhythm — this is the product)
1. Drop in the month's exports (GL, budget, sub-ledgers: CSV/XLSX from Dynamics 365 / Tally / SAP / QuickBooks / any ERP — file import is the guaranteed path; **no live ERP connectors in v1**).
2. Tool profiles, suggests mappings (saved profile auto-applies next month), validates, quarantines bad rows *with reasons*, checks control totals and trial balance.
3. Tool produces P&L / BS / CF, budget-vs-actual at the lowest shared grain, variance bridge, KPI set.
4. Tool runs 24 exception rules, assigns each finding an owner and due date; analyst works an inbox (explain / correct / waive-with-reason).
5. Tool refreshes the rolling forecast (method per account group, backtested), analyst adjusts drivers, compares Base/Upside/Downside.
6. Tool emits the board Excel pack + PowerPoint deck + PDF summary — cross-tied to the same numbers, every figure drillable to voucher → source file + row.
7. Optional (off by default): AI drafts variance commentary and exec summary from the *verified* tables; analyst edits before anything ships.

### 2.2 Personas
- **Primary:** the single FP&A analyst (non-technical; Excel-fluent). Success = month-end pack out in hours, not days.
- **Secondary:** accounting owners who receive findings; CFO/MD who reads the pack (never operates the tool).

### 2.3 Non-goals / anti-goals (v1)
No cloud, no login/multi-user, no ERP write-back, no live connectors, no consolidation/eliminations/FX translation (data model must not *block* it later), no statutory audit opinion (advisory disclaimer ships in-app), single reporting currency per project. **Anti-goal:** a tool that produces a number nobody can trace — worse than no tool.

### 2.4 Success metrics (numbers, not adjectives)
Month-end on the golden sample company: **≤ 30 min analyst time** (excluding owner responses); acceptance bars in §9 all green; 250k GL rows import+rules within the NFR budgets in doc 14; zero float-money defects; every exported figure ties across Excel/PPT/API in the cross-artifact test.

## 3. Architecture — modular monolith, one spine

```
ui/ (React+TS) ──HTTP 127.0.0.1──▶ app/api (FastAPI, thin)
                                      │
                               app/services/month_end.py   ← THE spine
                                      │
   imports ─▶ store (SQLite) ─▶ calc ─▶ rules (24) ─▶ forecast ─▶ exports (Excel/PPT/PDF)
                                      │
                               app/ai (optional, guarded, off by default)
```
- **One owner per concern** (attempt #2's B14, kept): `core/money.py` is the only money math; `store/schema.sql` the only schema; `calc/` the only statement logic; exports consume calc objects, never re-compute.
- **Deterministic core, AI at the edge:** AI receives only aggregated, verified figures; guardrails reject any AI text containing a number not in its input payload.
- **Offline-first:** binds 127.0.0.1 only; zero telemetry; works with network cable pulled (tested).

## 5. The three contracts that must never diverge again (K3 fix)
1. **Data dictionary ↔ schema:** `docs/02` lists every table/column; `app/store/schema.sql` implements it 1:1; a schema-equality test enforces it.
2. **Calculation spec ↔ oracle fixtures:** every formula in `docs/03`/`07`/`08` carries a hand-worked numeric example; the example *is* a test fixture, written before the engine code that must satisfy it.
3. **Canonical finding key:** `EXC-nnn|entity|account|period|grain-key` — defined once in `docs/07`, used by catalog, answer key, engine and acceptance harness. Any change = spec change + changelog + answer-key regeneration in the same commit.

## 6. Sample-data strategy (K2 fix — build the truth first)
`sample-data/generate_sample_data.py` (one work item) generates from **one financial plan**: budget authored → actuals = budget × (1 + controlled noise, seed-fixed) → only the 32 planted exceptions + 10 controls from `answer_key.json` (doc 42 §7–§8) deviate materially → balancing legs computed per entity×month, never hard-coded → byte-identical regeneration (hash-tested). Malformed corpus (≥10 files) ships with expected quarantine outcomes. **No rule code is accepted before this corpus + acceptance harness exist and run red for the right reasons.**

## 7. The execution model — one builder, one plan, one ledger (DEC-007)

The original plan deployed 500 accountable work packets across creator, tester and auditor agents. The owner has replaced that with **a single most-capable agent** that does every role in sequence. What survives from the old model is the part that mattered — accountable, file-sized, evidenced work — and what changed is who holds the accountability.

| Artefact | Role |
|---|---|
| `AGENT_PROMPT.md` (repo root) | The one prompt the builder follows: session protocol, work-item loop, spec-gap rules (class A/B/C), non-negotiables, self-verification protocol, handover format, forbidden list. |
| `docs/WORK_PLAN.md` + `.csv` | 241 work items in build order, grouped in milestones M0–M6, each with mission, dependencies (resolved to WI ids), inputs/outputs, acceptance criteria, paired test and the spec sections it must read. Generated by `tools/generate_work_plan.py`; never hand-edited. |
| `TASKBOARD.md` | The live ledger: status per item, handover evidence, owner questions, current position. The builder's memory across sessions. |
| `docs/17` §3/§4 | Open questions with labelled defaults; decision log. |
| `evidence/` | Test outputs, acceptance reports, milestone audits. |

**Coordination rules (how one agent doesn't produce attempt #5):**
1. **Milestones, not waves.** M0 docs hardening → M1 core + schema + corpus + fixtures + harness → M2 engine (acceptance gate turns green) → M3 services/API/CLI/AI → M4 UI → M5 exports → M6 ship. A milestone opens only when the previous gate is closed by an audit session (doc 86 §1, doc 34 §2).
2. **Contracts come from docs, never from code.** The builder may not invent a key, field, endpoint, error code or threshold. A gap is classified: design decision → OQ with labelled default, proceed; omission/contradiction → fix the owning doc first, then build; impossible → `blocked`, next item (`AGENT_PROMPT.md` §4).
3. **Repository as memory.** Every session starts by reading `TASKBOARD.md` and running the tests, not by recalling. Every item re-reads its cited spec sections. Nothing exists that is not written down.
4. **Evidence, not claims.** `done` requires pasted test output, ≥3 mutation checks that each broke a test, a scope diff and three spec-conformance checks in the handover block. Milestone audit sessions re-verify ten items chosen by number, run the audit streams (doc 34 §3) and write `evidence/audits/M<n>_audit.md`.
5. **Change the generator, not the output.** Plan corrections go into `tools/generate_work_plan.py`; the plan is regenerated and committed.

## 9. Quality gates (evidence-or-not-done)
- `scripts/check.py`: ruff + mypy (strict on `app/core`, `app/calc`, `app/rules`) + pytest + UI lint/type/tests + token/schema/docs parity checks. One command, honest exit code, no skip flags.
- `scripts/acceptance.py`: runs the harness twice, diffs findings, writes `evidence/acceptance_report.{json,md}`. **Release-blocking.** Bars (doc 14 §3 owns the numbers): recall 32/32 · controls 0/10 · High 18/18 · every extra finding justified · run-to-run identical · 24/24 rules wired.
- **Definition of Done (every work item):** file + paired tests + test output pasted in the handover + mutation checks + no deviation from the cited spec (or deviation logged as DEC). A `done` without evidence is reopened (K5 fix).

## 10. Audit plan (built into every milestone, not bolted on at the end)
Each milestone closes with a cold audit session (doc 34 §2) running the streams that apply: recompute (A), rule hunting (B), contract parity (C), adversarial (D), UX tabletop (E), truth (F), performance/soak (G), accessibility (H), export fidelity on a second-seed dataset (I), docs traceability (J), security review (K), release readiness (L). The owner may spot-check any `done` item at any time and ask for its commands to be re-run live.
