# 91 — BUILD-ORDER & DEPENDENCY SPECIFICATION (how `docs/WORK_PLAN.md` is sequenced and checked)

> Replaces the packet-dispatch rules of the multi-agent model (DEC-007). The machine-readable form is `docs/WORK_PLAN.csv` (columns `wi_id, path, layer, milestone, depends_on, …`), generated by `tools/generate_work_plan.py`. `scripts/docs_check.py` (M0 bootstrap) and `scripts/docs_check_release.py` (M6 full gate, DEC-014; doc 86 §1.1) enforces the rules below.

## 1. Rules
1. **Every work item has exactly one milestone** (M0–M6) and a `depends_on` list resolved to **WI ids**, not prose. The generator resolves each declared dependency string to the item that owns that path/contract and fails loudly if it cannot (an unresolved dependency is a generator defect, fixed in the generator — never in the output).
2. **Contract ownership is single:** a table is owned by `app/store/schema.sql`; an endpoint by its `app/api/routes_*.py`; a function by its module; a component by its file; a doc section by its doc (doc 00 §5). An item may *cite* any contract; it may *change* only the contracts of the file it owns.
3. **An item is startable** when every item in its `depends_on` is `done` in TASKBOARD with a handover block (not merely "file exists"). Items marked `exists-unverified` count as not done until re-verified.
4. **Order within a milestone** = topological order on `depends_on`, ties broken by layer rank (`config, core, store, data, imports, calc, rules, forecast, planning, adjust, services, api, cli, desktop, ai, ui, exports, scripts, packaging, ci, docs`) then by path. This is the order printed in WORK_PLAN and the order the builder follows.
5. **Standard dependency shapes:** UI screens depend on `app/ui/src/api/client.ts` + their route items + `theme/tokens` + the components doc 21 lists for them. Exports depend on calc + forecast + the report repo. Rules depend on schema + money + calendar + `rules/base`. Nothing at build time depends on a docs item (docs are baselined; M0 items are the exception and precede everything).
6. **A cycle, or a dependency on a later milestone, is a generator defect.** The generator asserts acyclicity and milestone monotonicity on every run.
7. **Mid-build contract change:** class-B rule (`AGENT_PROMPT.md` §4) → owning doc fixed → DEC if contract → the generator's items that cite the contract get their acceptance lines updated → regenerate → every `done` item that cites the changed section is set back to `queued (re-verify: DEC-nnn)` in TASKBOARD by the builder in the same session, found via the WORK_PLAN.csv `inputs`/`deps` columns.

## 2. Generator invariants (tested by the generator itself)
Unique `wi_id`; unique path; every dependency resolves; acyclic; milestone(dep) ≤ milestone(item); every item has a non-empty acceptance line and a paired test path (docs items: a `docs_check` rule instead); every M2 rule item names its fixture triple (`fires/silent/boundary`); every UI screen item names its route dependencies; gate text identical to doc 86 §1.
