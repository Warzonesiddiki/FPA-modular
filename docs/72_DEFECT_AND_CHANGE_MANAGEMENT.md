# 72 — DEFECT & CHANGE MANAGEMENT

**Defect lifecycle:** New → Triaged (severity: S1 wrong number/data loss/security; S2 wrong behaviour; S3 cosmetic; S4 docs) → Fixed (with failing-test-first evidence, doc 15 §4) → Verified (self-verification block + audit re-run, doc 34) → Closed. S1: stop-the-line (the current item pauses, owner informed same session), fix + audit-stream re-run (34). Defect record: template 87 (steps, dataset hash, expected/actual, screens, version).
**Change (RFC) flow:** idea → backlog (17 §5) → RFC (87 template: problem, options, spec impact, work-item impact, risk) → owner DEC → spec commit first (P2) → generator edited and WORK_PLAN regenerated; affected `done` items set to re-verify → build. Breaking data/API changes additionally require doc 61 migration plan and doc 05 version note.
**Baselines:** doc set baselined at Phase-0 approval (DEC-006) and at each release tag; TASKBOARD handovers cite the doc sections (and commit) they were built against; mid-milestone baseline changes re-open only the items citing the changed sections (the builder lists them in the DEC).
**Waivers of process:** none for S1/gates; any other waiver is a DEC with expiry (like finding waivers — process debt must resurface too).
