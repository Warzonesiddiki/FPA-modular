# 78 — TEST DATA MANAGEMENT SPECIFICATION

1. **Synthetic-first:** all dev/test/demo data is generated (doc 42). Real company data enters the repo **never** — not in fixtures, screenshots, bugs, or AI evals (72 defect template enforces: dataset hash or synthetic reproduction steps). The same rule covers the Dynamics 365 connector: recorded API pages in `tests/fixtures/connectors/` are generated from the corpus by `tools/mock_d365.py`, never captured from a real tenant; tokens in fixtures are synthetic strings; no tenant id, client id or environment URL of a real customer appears anywhere in the repo or CI configuration.
2. **Pilot data (on the client machine only):** stays in the client's project folder; if a defect needs their shape, the client may share an **anonymised extract** produced by the in-app anonymiser (Help → "Create anonymised sample": names/vendors/descriptions replaced with stable fake tokens, amounts scaled by a secret factor, dates shifted by whole months — structure and balance preserved, values unrecoverable). Anonymised extracts live outside the repo (support channel) and are deleted after the defect closes (35).
3. **Fixture governance:** fixtures carry source (generator version/seed or hand-oracle reference), a README per fixture folder, and hash in CI; changing a fixture requires the same review as changing a spec expectation (fixtures ARE expectations, doc 14 §2).


## Anonymiser specification (referenced in §2 — built as a support tool, M6)
Deterministic tokenisation: names/vendors/descriptions → `Vendor_###`/`Text_###` via a keyed hash with a client-held salt (same real value → same token, so duplicates/patterns survive; salt never leaves the client, tokens are irreversible to us); amounts × secret factor (client-chosen, recorded only as "scaled: yes" — ratios, percentages, TB balance and rule *patterns* mostly survive, absolute thresholds may shift and the defect report must say so); dates shifted by a whole number of months (seasonality survives, real dates hidden); account/entity codes kept (structure is the point) unless the client opts to tokenise them too. Output carries a manifest of what was transformed — a support engineer must be able to state exactly what the extract can and cannot prove.
