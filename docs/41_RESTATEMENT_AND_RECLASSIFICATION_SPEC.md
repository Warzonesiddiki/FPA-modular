# 41 — RESTATEMENT, CORRECTION & RECLASSIFICATION SPECIFICATION

## 1. Three distinct events (never conflated)
- **Source correction:** ERP data was wrong → fix in ERP, re-export, re-import (batch supersedes, doc 06). In-app history shows both batches; findings re-run; exports regenerated get new snapshot ids.
- **Reclassification:** presentation mapping changes (account moved to another statement line / cost centre restructure) → mapping/master change with `effective_from` period. Comparatives: reports offer `as originally reported | as reclassified` toggle; default for board pack = reclassified, stamped.
- **Restatement:** locked-period source data must change → unlock workflow (below).

## 2. Locked-period restatement workflow
1. Analyst requests unlock (period screen): POST unlock (doc 05 §7.4), expected_version and reason mandatory → period `locked → closing`, version +1, audit `RESTATE_OPEN`. The transaction first retains immutable pre-unlock snapshot references and old lock metadata; any failure rolls back and leaves the period locked. The prior sign-off remains historical, not current. 2. Correct via re-import (superseding batch) — old batch retained. 3. System produces a **Restatement Impact Report** (auto, before re-lock can complete): statements Δ per line (old snapshot vs new), BvA Δ, findings added/removed/changed, forecast runs invalidated (marked `stale` — never silently reused; rolling re-run required), reports superseded list. 4. Re-lock requires reviewing the impact report (checkbox attestation + note). 5. Prior exports remain on disk with their snapshot stamps — the new pack cross-references "supersedes report <id> dated …" on Cover.

## 3. Invariants
No silent history rewrite: every number ever exported remains reproducible from its snapshot (batches + mappings + layers are versioned, doc 24 §4). Findings closed on superseded data move to `explained` with system note linking the superseding batch (not deleted). Forecast-vs-actual history keeps the run's original base data hash.

## 4. Tests
Restate a locked golden period: impact report Δ matches hand-computed change; stale forecast flagged; re-lock blocked until attestation; as-reported vs as-reclassified toggle reproduces both statement versions; audit chain contains full sequence.

## 5. Current approval is not a reusable checkbox (DEC-020)
Sign-off and re-lock both require a nonblank approval note attached to a reviewed impact report for the exact immutable pre-unlock baseline and current after-input snapshot. The approval must identify that report and both snapshots in its retained history. Later source/mapping/layer/budget/forecast/commentary/finding changes that alter the report's inputs invalidate it; a different report or an earlier unlock cycle cannot satisfy it. A note on lock or generic close override is **not** this approval. Missing/stale approval remains ERR-083, reason=approval_note_required (no new code); refresh/regenerate impact and review it. Doc 05 §§8–9 specify the guards, impact generation/approval routes and fields; no runtime implementation is claimed.

The acyclic re-lock sequence is: corrected inputs → current forecast/approved commentary → checked pack → impact report for the original baseline and that current after-input snapshot → impact approval → sign-off → lock. Impact generation/reading does not itself alter financial inputs. Only forecasts based on superseded inputs are stale; a newly regenerated run matching current inputs must not be invalidated merely because impact is generated, or this would create another cycle. Later financial changes require refreshed impact and approval before the next sign-off.


## 6. Immutable comparison and currentness (DEC-021)
Doc 05 §9 owns the seven endpoint contracts. Unlock freezes a RestatementBaseline from the **last locked pack**, including original lock/sign-off metadata. A second unlock captures the most recent locked pack as a new baseline, never edits an earlier cycle. Report and approval records are immutable; source mutations invalidate their currentness, not their historical contents. A financial mutation followed by reversion cannot resurrect approval. Input-affecting mutations invalidate persistently; the impact/sign-off/lock audit events themselves are not financial mutations. No polling or background network call creates reports. "Auto" in §2 means the app offers and invokes the explicit generation command as part of the user-initiated restatement flow, not work on GET.

Compare the two retained project-total statement and BvA views for the same period/layer; never sum together different entities' fiscal periods or compare gl with gl_adj. Monetary comparison is after − before in presented major units via core/money (not raw ledger signs); include every changed cell, without materiality filtering. A changed cell has different numeric values or unavailable reasons; differing drill tokens alone do not create a monetary change. Two unavailable sides with the same reason emit no row; zero differs from unavailable. Input-only changes are still bound by the manifest hashes. A null/unavailable side stays labelled and delta=null, not coerced to zero. Retain source/file/row drill for each available side, including calculated-line child provenance. Union the old/new row grains; BvA grain collapse follows doc 03 §5 and is recorded in the frozen views. A changed grain appears as removed/added cells rather than pretending they are comparable. Monetary BvA measures are actual, budget, forecast, py and var_abs. Derived BvA ratios/favourability/materiality remain in each retained BvA view reachable by its source drill; this change stream is the monetary delta, not a replacement for the complete BvA viewer. Changes in input manifests require review even if all monetary deltas are zero.

Stable identity tuples (canonical JSON arrays, hashed for public key):
- statement: ["statement", statement, line_key]; all template rows including explicit zero rows; doc 45 owns keys.
- bva: ["bva", entity_id, account_id, cost_centre_id, measure].
- finding: ["finding", finding_key] (doc 07 owns the logical key). Compare retained business state: rule, severity, status, amount, owner, due/waiver, evidence, suggestion and correction state; omit evaluation timestamps/last_seen counters. Retain canonical before/after business-state hashes and ids. Added/removed refers to membership in the snapshot, not physical deletion; changed requires unequal hashes.
- forecast: ["forecast", run_id]; distinct runs invalidated by superseded inputs since baseline. The refreshed run used by the after pack is not invalidated just because a report was generated.
- report: ["report", report_id]; prior exports for the same period/layer whose manifests are superseded by after, excluding current-pack exports.

All rows are immutable and unique by (kind,key), sorted lexically; empty counts are legitimate. The before/after manifest hashes bind non-monetary changes too. **Hand-worked synthetic oracle:** revenue originally 100.00, corrected 125.00 → +25.00 presented delta even though source credits are negative. Budget 80.00 unchanged → BvA actual +25.00 and var_abs 20.00→45.00 (+25.00), budget emits no row. A newly present amount 0.00 versus absent → delta=null and before reason=absent. No change in any cells can still require approval when input provenance changes; do not mark a report approved based on counts=0.

Persistence is not implemented by these DTO tests. WI-0001 must still specify full snapshot-manifest storage, invalidation and impact/baseline/approval tables in doc 02 and assign their repository/service ownership in the generator before sign-off; the current schema.sql remains frozen. A schema id/reference is not proof that a historical snapshot is reproducible.
