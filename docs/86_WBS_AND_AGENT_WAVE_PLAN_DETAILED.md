### 1.1 Bootstrap versus release docs gate (DEC-014)
M0 includes verification tooling, **not product code**. WI-0008 builds `scripts/docs_check.py` after all seven doc-hardening items. It uses the standard library only, reads docs and the generated plan, imports no `app` modules and requires no unbuilt runtime/UI files. It returns deterministic file:line diagnostics and a non-zero exit for any defect; no skip flags or silent exclusions.

Bootstrap scope: numbered and unique sections in the seven hardened docs; local Markdown links and explicit doc/§ references in normative docs; definitions and references in the FR/ERR/EXC/screen/OQ/DEC/WI ID spaces; ERR/FR/settings-key **doc-to-doc** parity against docs 22/19/62 (not equality to the frozen code); doc 20 coverage of every doc-19 FR with valid planned WI/test paths; canonical period notation; no operational instructions for the retired multi-agent process; exact gate-text parity with the generator. Planned deliverable/test paths resolve against WORK_PLAN rather than falsely failing because M1–M6 have not been built. Historical audit/changelog/append-only decision text is not a current contract: clearly identified historical statements are exempt from current-count/retired-terminology checks, never from broken-link checks. Any further exclusion requires a documented rationale and a test, never blanket suppression. This is structural verification, not proof of semantic completeness: the seven acceptance lines and cold audit remain mandatory.

M6 retains the **full** gate as `scripts/docs_check_release.py` (the former M6 checker item, renamed to keep plan paths unique). It unconditionally calls all bootstrap checks and adds numbered-section coverage across docs 00–91, glossary coverage, planned-to-built-tree and FR-to-implemented-test/evidence parity, ERR/settings-to-code equality and OpenAPI-to-doc-05/90 parity. Missing code/evidence fails here. `scripts/check.py`, CI and the final docs audit call the release checker; bootstrap-only success cannot close M6. Each check in each script needs a planted-defect test; the release checker must propagate a bootstrap failure. Both gates stay in the plan; neither is implemented or claimed clean by this decision.

## 2. Ordering rules
1. **Strict milestone order.** No item of M*n+1* starts while M*n*'s gate is open. Exception: a `blocked` item (class C, `AGENT_PROMPT.md` §4) may be bypassed within the milestone, never across it.
2. **Within a milestone, WORK_PLAN order** (topological on declared dependencies, then layer rank, then path). The builder takes the first non-done item whose dependencies are done.
3. **Critical path:** M1 schema/corpus → M2 calc → M2 rules → acceptance gate. Protect it: when a class-A question touches it, apply the default and proceed the same session.
4. **Cut line (MASTER_PLAN §8):** if time is short, M4 screens S16–S19 and M5 report builder may ship in v1.1 by owner DEC — never the acceptance gate, cross-artifact tie-out, security suite or audit chain.
5. **Gate closure = audit session.** When every item of a milestone is `done`, the builder runs the milestone audit session (doc 34 §2) in a fresh session, writes `evidence/audits/M<n>_audit.md`, fixes defects, and only then marks the gate closed in TASKBOARD and `docs/00_INDEX.md` §10.

## 3. Capacity & estimates (for the owner's planning, not for pressure)
Items are sized so that one is typically one focused session (contract → tests → implementation → verification → handover). Rule and screen items are deliberately small and repetitive; corpus generator, acceptance harness, statements engine, Excel pack and desktop packaging are the large ones (expect 2–4 sessions each and plan a mid-item handover note in TASKBOARD). Progress is reported as the gate table above with counts from TASKBOARD, never as percentages of "feel".
