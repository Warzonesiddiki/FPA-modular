# 23 — STATE MACHINES & WORKFLOWS

> Every lifecycle in one place; code (workflow modules) implements exactly these transitions; illegal transition = ERR-040/080. All transitions write audit + history.

## 1. Period: `open → closing → locked → (unlock→) closing`
Enter `closing` only through POST start-close (doc 05 §7.3), not by opening S16 or reading a checklist; `locked` via lock action (FR-PRJ-003 guards). Imports into `locked` rejected; into `closing` allowed with banner. Start-close accepts only open; unlock accepts only locked and requires a note. Both require expected_version, increment it exactly once and write audit atomically (doc 05 §7). Unlock records RESTATE_OPEN and retains the immutable pre-change baseline before allowing correction; it clears current lock metadata but not history and invalidates the prior sign-off for current readiness. It does not reset or reinstantiate the task template.

## 2. Import batch: `staged → validated → committed | rejected | superseded`
`staged` on upload; `validated` after the validation stage completes with no blocking issue (quarantine may be non-empty; ERR-022/023 keep the batch `staged`); `committed` only via atomic commit passing control totals and the TB gate (doc 06 §2 steps 6–8); `rejected` = analyst discard (staging removed, audit kept); `superseded` when the same (file-hash, period, kind) is recommitted. Crash in commit → stays `validated` (never half-committed; doc 06 §2 step 7). Re-validation after a mapping change returns the batch to `staged` first. Only `staged`/`validated` batches can be discarded; `committed` batches can only be superseded.

## 3. Finding: `new → acknowledged → explained → corrected → verified → closed`; `waived` from any non-closed state
Guards: corrected needs a reference — an applied adjustment created from the suggestion, a rectification-journal export containing the finding, or a typed re-import batch / journal reference (doc 07 §7.4); verified needs a re-run where the finding no longer fires OR the correcting lines matched in a later committed batch (system-proposed, analyst confirms; auto-confirm is a setting, default off) OR an evidence-accept note; waived needs reason + expiry ≤90d → auto-returns to `new` on expiry (job on app open + on rule run). Re-firing of a closed finding (same key, later run) reopens as `new` with history preserved. **Forward skips are allowed** (a finding may go `new → corrected` directly when the analyst applies the suggested adjustment or successfully exports its rectification journal; queueing alone does not mark a finding corrected (doc 07 §7.4); the skipped states are recorded as implied in history); backward moves are not, except `waived → new` on expiry and `verified → new` when the finding re-fires after verification (the correction did not hold — history keeps both).
## 4. Forecast run & scenario: run `draft → locked` (immutable); scenario `draft → applied-view → saved`; sandbox what-if has no persistence state (session only).
## 5. Budget version: `draft → approved → locked`; BvA default compares latest locked, analyst may select approved (labelled in exports).
## 6. Commentary: `draft → approved` (exports read approved only); AI drafts enter as draft w/ provenance; editing an approved commentary creates a new draft version.
## 7. Close task: `not_started → in_progress → done | blocked | waived(reason)`; period sign-off requires all tasks done/waived + zero blockers (TB, high findings, stale forecast, exports) or override note.
## 8. Recon: `open → in_review → signed_off`; sign-off guard ERR-081 (tolerance).
## 9. Alert: `active → acknowledged → dismissed(auto after period lock)`; deduped by key.
## 10. Report: `generating → ready | failed(checks)`; ready reports immutable, regeneration = new report row.
## 11. Dynamics 365 connection (per project; doc 26 §8): `not_configured → configured` (PUT settings) `→ signed_in` (sign-in or application-mode test OK) `⇄ token_expired` (silent refresh fails → ERR-112; *Sign in again* returns to `signed_in`) `→ disconnected` (Disconnect: keyring wiped, settings kept; PUT/sign-in returns to `configured`/`signed_in`). Derived, not stored: computed from settings + keyring presence + last refresh result. **Pull** (`connector_pulls.status`): `running → snapshot_written → staged` | `running → no_change` | `running|snapshot_written → failed(ERR-11x)`; a `failed` pull leaves no batch and no snapshot file (written to a temp name, renamed only on success); cancellation = `failed(cancelled)`. Guards: pull refused when the period is locked (ERR-027; doc 22 import-lock code, including connector staging) or another pull is `running` for the same project (ERR-092 wording "busy").

## Month-end happy-path workflow (the spine, services/month_end.py)
(Pull from Dynamics 365, when connected →) Import commit → TB gate → statements snapshot → rules run → findings triage → forecast run+lock → commentary approve → checks → board pack → close sign-off → period lock. Each step's completion is derived from the state machines above (never a manually-ticked checkbox pretending completion — S01/S16 read real states; manual tasks in S16 are the only human-attested items, and they say so).
