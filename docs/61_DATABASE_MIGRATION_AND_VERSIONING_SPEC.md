# 61 — DATABASE MIGRATION & VERSIONING SPECIFICATION

1. **Versioning:** `schema_meta(version INT)` single row. Migrations are numbered SQL+Python steps `m0001…` in `app/store/migrations/` registered in db.py; each has `up(conn)`, a description, and the app version that introduced it. Never edit a shipped migration — append.
2. **On open:** app reads version; if behind → **backup first** (timestamped copy in `backups/pre-migration-<v>-<ts>.db`, verified by hash), then apply sequentially in one transaction per migration; failure → rollback that migration, original DB untouched, ERR-091 with backup path. If DB newer than app → read-only open + message (doc 16 §2).
3. **Fixtures:** CI keeps real project DBs generated by each released version (`tests/fixtures/db/v1.0.db` …); opening each with current code and running smoke+acceptance-mini is a release gate (16 §4).
4. **Rules for authors:** additive-first (new tables/columns nullable or defaulted); renames = new column + copy + (next major) drop; money columns stay INTEGER minor units; every migration ships with an up-fixture test proving row counts + spot values survive; migrations never call network/clock (timestamps injected).
5. **Sample project** is regenerated, never migrated (flag `is_sample` → rebuild on version change).
