# 44 — RULE ALGORITHMS, DETAILED (appendix to doc 07)

> Doc 07 owns *what* each rule flags + the canonical key format. This doc owns the exact algorithm, so an implementation written from this text alone produces identical findings to the answer key (doc 42). Thresholds come from settings keys `rule.EXC-###.<param>` with the defaults in doc 07 §1.

## 0. Common definitions (apply to every rule)
- **Input rows:** committed `gl_rows` of the project for the run's layer (`gl` default; `gl_adj` adds applied `adjustments`, doc 39 §3) for the target period plus the rule's lookback window. Amounts are integer minor units.
- **Spend** of an (entity, account[, vendor]) in a period = Σ `amount_minor` of its rows in that period, **debit-positive** (credits reduce it); for revenue-type accounts the sign is flipped so spend is a positive magnitude. Where a rule says "amount" of a voucher it means |Σ debit legs| of that voucher.
- **Manual journal** = a row whose batch has `import_batches.is_manual = 1` (doc 02; set from the mapping profile's `is_manual_journal` flag or the import wizard checkbox) **or** whose `voucher_no` matches the project setting `rule.manual_prefixes` (default `JV,MJ`). Both conditions are evaluated; evidence names which one matched.
- **Tags** are read from `accounts.tags` (doc 02 §2 closed list): `suspense`, `accrual`, `contra`, `accrual_balancing` (system balancing legs, EXC-023). Untagged projects → the rule runs on the empty set and reports `not_run: no accounts tagged <tag>` (counted, doc 07 §5).
- **Lock evidence (EXC-005):** `periods.locked_at` + `finding` evidence lists rows whose `posting_date` falls in a period whose status is `locked` **and** whose batch `committed_at > periods.locked_at` of that period. Rows committed before the lock are legitimate.
- **Short history:** each rule states its minimum lookback (periods with committed GL for the entity). Below the minimum the rule returns `not_run` with reason `insufficient_history:<have>/<need>`; it never runs on a partial window silently. Minimums: EXC-006 3 · 008 3 · 009 6 · 013 3 · 014 6 · 015 6 · 016 6 · 019 3 · 020 0 · 024 6 · 025 6 (of a 12-period window) · 026 0 periods but ≥ `min_history_count` prior lines per group (groups below it are skipped and counted in evidence, not `not_run`) · 027 6 · 028 0 (needs only the rows of the previous `window_days` days, which may sit in the prior period); rules not listed need only the current period (and the budget version for 017/018/019).
- **Boundary semantics:** `≥` means fires at the threshold exactly; `>` means strictly above (EXC-004 tolerance, EXC-007 age). Tests encode both sides (§ boundary matrix).
- **Vendor** of a row = `gl_rows.vendor_id`, whether it came from a mapped column (`vendor_source = column`) or from the AP sub-ledger enrichment step (`vendor_source = ap_match`, doc 06 §2 step 9). Rules that need a vendor (006, 014, 015, 021, 026, 027-vendor-grain, 028) return `not_run: no_vendor_column` when the project has **no** row with a vendor in the window; rows without a vendor are skipped and counted in evidence (`skipped_no_vendor`).
- **P&L accounts** = accounts whose statement_line maps to the P&L (revenue, COGS, opex, other income/expense, depreciation, interest, tax — doc 45). Spend/variance rules 006, 008, 012, 013, 015, 017, 018, 019, 020 and 025 run on P&L accounts only; balance-sheet accounts are covered by 007, 011, 016, 022, 024, 026, 027, 028 (which run on all accounts). A rule's scope is part of its contract: a P&L-only rule firing on 1400 Fixed Assets is a defect (doc 42 P34 relies on this).
- **Narration tokens (EXC-025, EXC-007 suggestion):** lowercase the description; replace every character that is not a letter with a space; split; drop tokens shorter than 4 characters and tokens in `rule.EXC-025.stopwords` (default: `being, towards, payment, paid, invoice, bill, charges, month, amount, against, from, with, this, that`); a row contributes each distinct token once. The **association table** for an entity is built from the prior 12 periods' committed rows on P&L accounts: `count[token][account]`; `total[token] = Σ_accounts`; a token is *usable* when `total[token] ≥ min_token_count` (12). Share of token t in account A = `count[t][A] / total[t]` (Decimal, 4 dp, half-up). The table is rebuilt per run from the layer's rows (no cache across runs), so it is deterministic for a given corpus.
- **Median** = the middle value of the sorted |amount| list; for an even count the lower-middle value (integer minor units, no averaging — keeps everything integral and deterministic).

## Per-rule algorithm (pseudocode pattern: SCOPE → GROUP → TEST → EMIT)
- **EXC-001** GROUP (entity, voucher_no): collect batches; if same |amount| multiset appears in ≥2 batches OR duplicate rows in-batch without an equal opposite-sign row within the group → EMIT per voucher, grain=`voucher_no`, evidence: batch ids + row ids both sides.
- **EXC-002** JOIN current batch rows to prior committed rows on (entity, voucher_no, account, amount, posting_date): any hit → EMIT grain=`voucher_no|account`.
- **EXC-003** Recompute batch totals from gl_rows; compare stored control totals; Δ≠0 → EMIT grain=`batch_id` (also blocks at commit per doc 06; this catches post-hoc tampering).
- **EXC-004** GROUP (entity, voucher_no): Σamount; |Σ| > tol → EMIT with all row ids.
- **EXC-005** Rows in a `locked` period whose batch was committed after `periods.locked_at` (§0 lock evidence): EMIT per voucher, grain=`voucher_no`, evidence: locked_at, committed_at, batch id.
- **EXC-006** GROUP (entity, account, vendor) period spend share; prior-3 avg share; TEST share ≥40% AND spend ≥ spike_abs AND prior avg <25% → EMIT grain=`vendor`.
- **EXC-007** Accounts tagged suspense: net balance at period end; oldest unmatched voucher age via FIFO offsetting (debits vs credits chronological); TEST age >30d OR |balance| ≥ material_abs → EMIT grain=`account`, evidence: oldest voucher + ageing buckets 0-30/31-60/61-90/90+.
- **EXC-008** Manual vouchers (§0) to P&L accounts with amount ≥ one_off_abs (₹1,000,000): lookback 3 periods for a voucher on the same account with amount within ±5%; none → EMIT grain=`voucher_no`.
- **EXC-009** Requires poster/time columns (else not_run): poster ∉ usual set (posters covering ≥80% of account's vouchers in 6 periods) OR hour 0–5 OR Sat/Sun → EMIT Low grain=`voucher_no`.
- **EXC-010** |doc_date − posting_date| spans period boundary AND |amount| ≥ material_abs → EMIT grain=`voucher_no`.
- **EXC-011** Accrual-tagged vouchers (or description match list): search next period for offsetting row (same account, opposite sign, |amount| within 1%): none → EMIT grain=`voucher_no` (original).
- **EXC-012** Contra-normal postings. Expense accounts (type opex/cogs, not contra-tagged): sum credit-side (negative) rows; revenue accounts (not contra-tagged): sum debit-side (positive) rows; in both cases exclude pairs that exactly reverse an opposite row in the same/prior period (same |amount|, same account, ≤45d): net ≥ material_abs → EMIT grain=`account`, evidence names the side (`credits_to_expense` | `debits_to_revenue`).
- **EXC-013** Account period spend vs average of prior 3 periods' spend: Δ = spend − avg; AND-test Δ ≥ spike_abs AND Δ/avg ≥ spike_pct → EMIT grain=`account`, evidence: the three prior values. Zero prior avg: fires only if spend ≥ 2× spike_abs (pct leg n/a, recorded). Severity High when Δ ≥ 3× spike_abs AND Δ/avg ≥ 3× spike_pct.
- **EXC-014** Vendor's account set over prior 6 periods; new account this period with amount ≥ material_abs → EMIT grain=`vendor|account`.
- **EXC-015** Vendor+account active ≥5 of prior 6 periods (median amount m): absent this period → EMIT Medium grain=`vendor|account`, evidence m. (If project history <6 periods → not_run with reason until enough history.)
- **EXC-016** Accrual-tagged accounts monthly in ≥5/6 prior periods: this period missing or <50% of median → EMIT grain=`account`.
- **EXC-017** BvA grain actual ≥ material_abs AND budget line absent/0 → EMIT grain=`account`.
- **EXC-018** Doc 03 §5 AND-test exactly; severity escalates at ≥3× both legs → EMIT grain=`account`.
- **EXC-019** YTD var ≥ material_abs AND monthly overrun strictly increased 3 consecutive periods → EMIT grain=`account`.
- **EXC-020** Vouchers with amount mod round_amount == 0: count ≥5 AND Σ ≥ spike_abs AND share of account voucher count ≥30% → EMIT Low grain=`account`.
- **EXC-021** GROUP (entity, vendor) sliding 7-day windows: ≥3 vouchers each < approval_limit, Σ ≥ 1.5×limit → EMIT High grain=`vendor`, evidence window + vouchers. Windows evaluated on posting_date sorted; overlapping windows merged into one finding (max Σ window).
- **EXC-022** Same account, debit row and credit row |amount| equal, dates ≤5d apart, different vouchers, and pair nets the account's period movement by ≥90% → EMIT grain=`account|amount_minor`.
- **EXC-023** Voucher line-count == 1 AND |amount| ≥ material_abs AND the row's account is not tagged `accrual_balancing` (§0) → EMIT Low grain=`voucher_no`.
- **EXC-024** Account's last activity ≥6 periods ago (or created_at in period) AND period |total| ≥ material_abs → EMIT Low grain=`account`.
- **EXC-025** Account–narration mismatch. SCOPE current-period rows on P&L accounts with |amount| ≥ min_abs (₹25,000). Build the entity's association table (§0) from the prior 12 periods (need ≥ 6 periods with committed GL, else `not_run insufficient_history`). For each row: tokens = usable narration tokens of its description; **signal tokens** = tokens t with some account A* ≠ row.account such that share(t, A*) ≥ dominance_pct (90%) AND share(t, row.account) ≤ 2%. TEST: ≥ min_signal_tokens (2) signal tokens name the **same** A* → EMIT Medium grain=`voucher_no` (one finding per row; a voucher with two offending rows → two findings, grain `voucher_no|row_no` for the second and later rows), evidence: tokens with counts/shares, A*, row id. Rows whose description has no usable token are skipped (counted). Ties between two A* candidates → pick the one with more agreeing tokens, then the higher summed share, then the lower account code — recorded. Suggested account = A*.
- **EXC-026** Amount outlier / decimal shift. SCOPE current-period rows with a vendor (all account types). GROUP (entity, vendor, account); history = the group's rows in the prior 12 periods (current period excluded; no other filtering — the median is robust to earlier outliers, see doc 42 C12, and this keeps the rule independent of run order); skip the group when history count < min_history_count (6). typical = median |amount| of history (§0). ratio = |amount| / typical as Decimal (6 dp). TEST: (ratio ≥ outlier_factor (5) OR ratio ≤ 1/outlier_factor) AND | |amount| − typical | ≥ min_abs (₹25,000) → EMIT grain=`voucher_no`. `decimal_shift_suspect` = ratio (or 1/ratio) within ±shift_tolerance_pct (2%) of 10, 100 or 1000; `shift_factor` recorded. Severity: High when ratio ≥ 100 (or ≤ 1/100) **or** |amount| ≥ 3 × material_abs; else Medium. Evidence: history count, min/median/max, ratio, shift factor. Not_run only when no row in the window carries a vendor (§0).
- **EXC-027** Unusual cost centre. SCOPE current-period rows with a cost centre and |amount| ≥ min_abs (₹25,000). GROUP (entity, account, vendor) when the row has a vendor, else (entity, account). History = group rows in the prior 6 periods (need ≥ 6 periods of committed GL, else `not_run`); skip groups with < min_history_rows (10). dominant set = the smallest set of ≤ 2 cost centres covering ≥ dominant_share_pct (90%) of history rows (by row count); if no such set exists the group is "spread" and skipped (counted). TEST: row.cost_centre ∉ history cost centres AND group not spread → EMIT Low grain=`voucher_no`, evidence: history rows by cost centre, dominant set with shares. Suggested cost centre = the single most frequent historical cost centre (ties → the one with the larger Σ|amount|, then lower code).
- **EXC-028** Near-duplicate vendor charge. SCOPE rows with a vendor and |amount| ≥ min_abs (₹25,000) in the current period **plus** the preceding window_days (30) of the prior period(s) as anchors only. Sort by (posting_date, voucher_no, row_no). Walk in order keeping `anchors` per key (entity, vendor, account, |amount|, sign): for row R, if an anchor Q exists with `R.posting_date − Q.posting_date ≤ window_days` and `Q.voucher_no ≠ R.voucher_no` → EMIT on R (current period rows only) grain=`voucher_no`, evidence both rows, day gap; R is **not** added to anchors. Otherwise R becomes an anchor (replacing an older one for the key). Same-voucher repeats are EXC-001's; an exact opposite-sign row within the window (a reversal) removes its anchor instead of firing. Severity Medium; escalation base material_abs.

## Suggestion derivations (data-dependent parts of doc 07 §7.3)
- **Dominant account for a vendor (EXC-014 reclass):** over the prior 6 periods, the vendor's account with the largest Σ|amount|; share = that Σ / vendor total; confidence high if ≥ 95%.
- **Proposed account for suspense (EXC-007 clear_suspense):** if the suspense rows carry a vendor → the vendor's dominant account (above) when share ≥ 60%; else the EXC-025 association table applied to the suspense rows' descriptions (≥ 2 agreeing signal tokens); else `investigate`.
- **Repost amount (EXC-026 reverse_and_repost):** `decimal_shift_suspect` → |amount| ÷ shift_factor (exact integer division is guaranteed only when the amount is a multiple; otherwise round half-up to the minor unit and say "approximately" in `basis`); not a shift → the median, confidence low.
- **Dominant cost centre (EXC-027 reclass_dimension):** as in the rule's EMIT; confidence high when the dominant set is a single cost centre holding 100% of history rows.
- **Accrual amount (EXC-015/016 accrue):** median of the prior-6 charges/accruals for the group (§0 median).
- **All journal kinds:** lines are built debit-positive from the perspective of the correcting entry, Σ = 0 asserted before the suggestion is stored; the posted row's `source_account_ref` (doc 02) is copied onto the reversing/credit leg so an ERP export can address exactly the original ledger-account string.
- **Verification match (doc 07 §7.4):** a committed row matches a suggestion line when entity and account are equal, |amount_minor| is equal, the sign equals the line's sign, posting_date ≥ the suggestion's consumption date, and (description contains the tag `[FPA EXC-### <voucher>]` **or** the row's voucher has the other leg(s) of the suggestion too). All lines matched → propose `verified`.

## Boundary test matrix (mandatory per rule in tests)
Threshold −1 minor unit (silent), threshold exact (fires unless spec says >), threshold +1; pct boundary ±0.01%; zero-budget/zero-prior variants; lookback-insufficient → not_run. Entry-hygiene rules add: EXC-025 one-signal-token (silent) / two (fires) / two tokens naming different accounts (silent); EXC-026 ratio 4.99 (silent) / 5.00 (fires) / 9.8–10.2 (shift flag) / 99.9 vs 100 (Medium vs High) / inverse ratio 0.1; EXC-027 dominant share 89.9% (spread, silent) / 90% (fires) / 9 history rows (skipped); EXC-028 gap 30 d (fires) / 31 d (silent) / same voucher (silent, EXC-001's) / reversal pair (silent) / chain of three (one finding). The acceptance plants (doc 42 §7) sit ≥10% inside thresholds so boundary noise cannot flip recall; the controls (doc 42 §8) each target one specific wrong implementation and must stay silent.
