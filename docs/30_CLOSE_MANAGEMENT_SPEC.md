# 30 — MONTH-END CLOSE MANAGEMENT SPECIFICATION

## 1. Close calendar
Per project: close start = period end + offset business days (setting, default T+1), target lock day (default T+5 business days, holiday list per project — manual list v1). Calendar view S16 shows tasks on business days, overdue in words + colour (never colour-only).

## 2. Default task template (instantiated per period; owners pre-filled from master data)
T-01 Import GL & subledgers (system-verified: batch committed) · T-02 Trial balance balanced (system; when an ERP trial-balance file was imported for the period, also zero per-account tie-out differences — doc 06 §1 `tb_check`) · T-03 Bank/AR/AP/payroll reconciliations signed (FR-REC) · T-04 Statements reviewed (attest) · T-05 Material variances explained (system: material BvA rows all have approved commentary) · T-06 Exceptions triaged (system: no `new` high findings, and no finding `corrected` more than 2 periods ago whose correction is still unseen in the ledger — doc 07 §7.4) · T-07 Forecast refreshed & locked (system) · T-08 Board pack generated, checks green (system) · T-09 Close sign-off (attest) · T-10 Period locked (system). System-verified tasks complete themselves from real states (doc 23 §7 and month-end workflow); attested tasks need a named human click + optional note. Custom tasks addable (title, owner, due offset, dependency) — template edits apply to future periods only.

## 3. Blockers & escalation
Blocker = unmet system condition for sign-off/lock; shown on S01/S16 with deep links. Overdue tasks → alerts (FR-ALR) at due+1. Close cycle days (period end → lock) recorded per period → KPI + trend on S01 ("close is getting faster/slower" — the product's core promise, measured).

## 4. Sign-off record
Attestation text ("I confirm the pack for <period> is complete and reviewed"), signer label, timestamp, snapshot ids — stored, shown on Excel Cover and S16 history. Sign-off ≠ statutory certification (advisory wording applies).

## 5. Starting and reopening close (DEC-018)
POST start-close (doc 05 §7.3) creates the period template exactly once in the open→closing transaction; GET close/S16 navigation never mutates state. It completes no attest/system task merely by creating rows. Unlock (§7.4) retains task history and the old sign-off, invalidates current readiness, and does not recreate the template. Sections 6–7 resolve the T-09/T-10 cycle and define non-bypassable sign-off/lock guards; impact generation/approval transport is specified in doc 05 §9.

## 6. Acyclic readiness and permitted exceptions (DEC-020)
T-01…T-08 are prerequisites. T-09 is the **result of successful sign-off**, and T-10 is the **result of successful lock**; neither is a prerequisite to itself or to sign-off. Custom task dependencies must be acyclic and cannot point at T-09/T-10. An absent checklist is not an empty satisfied checklist: start-close must have instantiated it first. System tasks are derived from current evidence, never manually marked done or waived. T-04 remains a named human attestation; custom manual tasks can be waived with a recorded reason. Reading readiness neither instantiates tasks nor writes completion rows, runs rules, refreshes data or creates reports.

The closed blocker register below drives doc 05 §8. Count is the number of offending resources for high_findings, manual_tasks and busy; all other aggregate checks use count=1 when unsatisfied. Omit satisfied rows, sort by code, emit each code once. The fingerprint retains the sorted offending resource identities, not just counts, so replacing one finding with another is not the same review. System/attest/custom prerequisite failures map to their owning check; a missing/cyclic/invalid template maps to statements_review and cannot be bypassed.

| Code | Unsatisfied condition | Overridable |
|---|---|---|
| audit_integrity | Known broken audit chain / integrity read-only state | no |
| busy | Active/queued period-affecting job or incompatible write/lifecycle lease | no |
| period_state | Period is not closing | no |
| no_gl | No committed GL batch for the period (a validated committed zero-activity batch is distinct from no import) | no |
| trial_balance | Any entity's TB is not balanced; an earlier analysis waiver does not make it balanced | no |
| tb_tie_out | An imported ERP TB has unresolved per-account differences | no |
| reconciliations | Required bank/AR/AP/payroll reconciliation sign-offs missing or stale | no |
| statements_review | T-04 not attested for current statements, or template/dependency integrity failure | no |
| material_variances | Material BvA commentary absent, unapproved or stale | no |
| rules | No current completed rule run accounting for all 28 rules (executed or explicit not_run reason); no run is not zero findings | no |
| high_findings | High finding not closed and not effectively waived at the injected evaluation time | yes |
| aged_corrections | Corrected finding more than two periods old still unseen in the ledger (doc 07 §7.4) | no |
| forecast | Forecast missing, unlocked or stale against the current financial inputs | no |
| board_pack | Required Excel/PPT pack missing, failed checks, mismatched snapshots or stale financial inputs | no |
| manual_tasks | Custom manual prerequisite not done/validly waived, including its unresolved manual dependencies | yes |
| restatement_review | Reopened period lacks a current approved impact report with a nonblank approval note | no |

A sign-off override note can cover **only high_findings and manual_tasks**; record the exact overridden rows and review fingerprint. It never marks the task done or removes a finding. All other conditions are hard stops, irrespective of note, force flag or prior waiver. This narrows the earlier blanket 'or override note' wording rather than weakening a gate. Only the lock endpoint's force=true plus a nonblank note permits remaining High findings at lock, and only when the current sign-off already approved that exact review. Neither force nor sign-off overrides a missing/stale impact approval.

## 7. Review binding and sign-off durability (DEC-020)
Doc 05 §8 owns DTOs and token bytes. Evaluate readiness against one consistent project read snapshot and an injected clock. Exclude the evaluating request's own lease from busy; otherwise acquiring the mutation lease would block itself. Other incompatible leases/jobs still block. The review binds project/period/version, current project audit head, selected immutable financial snapshot and the full blocker fingerprint. Financial inputs must match the pack manifest (doc 24 §4), not merely the batch watermark. Effective waiver expiry and any state change are re-evaluated before signing/locking, even if no background expiry job has run.

Sign-off appends an immutable close_signoffs record and one CLOSE_SIGNOFF audit event (entity_type=close_signoff, entity_id=signoff_id) atomically. It creates a record; it does **not** change period.version or lock the period. While closing, T-09 is a projection of a current valid record; while locked, T-09 shows the retained sign-off linked by PERIOD_LOCK, not a fresh authorisation to lock again. T-10 shows the lock itself. The generic task editor cannot complete T-09/T-10; only their dedicated commands establish those outcomes. After unlock the old outcomes remain historical and T-09 is not current. Its audit event hashes the stored fields, not its own resulting hash. To be current, the event must be the **latest project audit event**, the period/version/snapshot must still match, and the recomputed blocker fingerprint must equal the approved one. A new sign-off replaces only which record is current, never historical rows. The deliberately conservative v1 rule invalidates sign-off on any subsequent project mutation, including another period; GET polling is not a mutation. Re-sign after changes. Optimising to domain-specific revision tracking is deferred, not silently inferred.

Lock rechecks all guards and the same sign-off under an exclusive period-write boundary, then atomically changes closing→locked, increments period.version once, sets injected locked_at/updated_at and lock_note, writes PERIOD_LOCK with the signoff_id, and publishes its receipt. T-10 is a projection; do not write a second task-update audit after sign-off before checking its binding. Lock retains the snapshot and sign-off link for history and unlock baseline capture. DEC-022: its retained audit evidence includes CloseLockRecord (05 §10), and effective task statuses are frozen in locked_status in that same transaction; no separate post-sign-off task audit is inserted. Failures leave period/tasks/sign-off history untouched. A stale review produces ERR-080 with blocker review_changed; callers refresh readiness. Current-signoff absence/staleness produces ERR-080 with blocker signoff_required. Wrong period state is ERR-016; audit break ERR-090; busy ERR-092; remaining High without force ERR-011; absent/current-impact approval ERR-083. Force without a valid note is ERR-015.

Task/calendar/template and close-history APIs are specified in doc 05 §10 (DEC-022). Impact transport is specified in doc 05 §9; a current immutable approval, not a client flag or historical record, satisfies restatement_review. These document contracts are not runtime implementation.


## 8. Task editing and template isolation (DEC-022)
One project template, revision ≥1, is persisted at project creation, including sample workspaces. This does not instantiate period tasks or complete anything. Start-close atomically copies its calendar and entries into the selected period once; future template changes never rewrite existing period tasks, dates or completions. Unlock reuses that period copy. Template and period task writes are owned by period_repo; close_service owns guards/projections; core/calendar owns business-day arithmetic. GET never creates template/tasks, writes derived status or appends audit. Missing template on a migrated project is a migration defect, not permission for GET to repair it.

Ten mandatory task keys T-01…T-10 retain their §2 titles and kinds; no deleting, renaming, changing kind or adding dependencies to these built-ins. Owners and due offsets are editable. T-09/T-10 are special outcomes despite their historic attest/system kinds, never direct transition targets. Custom keys C- plus 1..24 lowercase letters/digits/underscore (first a letter), kind=manual, can be added/removed only in the **future template**. Total template size 10..1000. Each entry has at most one dependency (doc 02's existing scalar relation); it must reference another entry, cannot reference T-09/T-10, and the entire graph must be acyclic. Reject duplicate keys, self/cross-period/missing references and cycles; do not silently drop an edge. Default dependencies are null; built-in system conditions, not a fake dependency chain, enforce prerequisites. All custom manual entries are close prerequisites.

Initial owner_id=null (no guessed person); the analyst can select active project owners in the template. Existing inactive assignments remain readable and may be kept unchanged; a new assignment to an inactive owner is ERR-044, foreign/missing owner is ERR-001. At start-close, a now-inactive template owner becomes null in the period copy and the start-close audit records each cleared key; nothing is silently discarded. Template titles come from §2; default due offsets: T-01/T-02=1, T-03=2, T-04/T-05/T-06=3, T-07/T-08=4, T-09/T-10=5. T-09/T-10 template offsets must equal the calendar's target lock day. Custom titles are bounded literal text (doc 05); no executable markup/formulas.

Live task edits only while closing: details (custom title/dependency, any owner/due offset) or human transition. No adding/removing tasks in a live period; use the future template. Expected task AND period versions plus a fresh review token are required; task revision increments once, period revision does not change. Details edits to a custom task reset its requested status to not_started and clear current attestation; historical audit remains. Built-in details edits do not revoke T-04's statements attestation unless statement inputs changed. Every successful edit invalidates current close sign-off via its project audit event. Both details and transitions append CLOSE_TASK_UPDATE + receipt atomically; no extra derived-status audit on GET.

Human transitions: T-04 and custom manual tasks may move to not_started/in_progress/blocked/done; only custom manual tasks may become waived. Forward skips are explicit, not implied completions. Reversals and same-state re-attestations are allowed, audited: moving away from requested done/waived needs a nonblank note. blocked and waived always need a note; done/waived require signer + attest=true; other targets require signer=null and attest=false. done/waived requires any dependency to be currently done or validly waived (otherwise ERR-084), not merely to have a historical completion. System tasks and T-09/T-10 reject all manual transitions, even a no-op or force flag. A generic override never marks a system task done.

Effective status is a read projection. For system tasks: done when the §6 owning checks are satisfied, otherwise blocked. T-06 uses high_findings AND aged_corrections AND rules (not just zero new findings); T-02 uses trial_balance AND tb_tie_out; T-01=no_gl; T-03=reconciliations; T-05=material_variances; T-07=forecast; T-08=board_pack. T-04 starts not_started, and its done attestation is current only for the exact reviewed **statements** fingerprint. Statement-input changes permanently revoke that attestation, even if values later revert; a new explicit attestation is required. Forecast/commentary/pack generation by itself does NOT change that fingerprint, avoiding a T-04→forecast→pack→T-04 cycle. Doc 24 §4 owns financial provenance; statement fingerprint is the manifest subset of GL/opening/adjustment/mapping/master/presentation-setting versions used by current PL/BS/CF, including prior-period inputs used by those statements. Missing current statements blocks done (ERR-080 statements_review); no checked-pack prerequisite for T-04.

Manual effective status equals requested status except that any unresolved dependency makes it blocked. Manual done/waived is a checklist attestation, not financial approval: it can become effective again when its dependency is resolved, but cannot authorise lock without fresh readiness/sign-off. T-04 stale done is blocked. T-09 is done only for current sign-off while closing, or the retained lock-linked sign-off while locked; T-10 done only while locked. Otherwise these outcomes are not_started. Locked task projections use retained lock evidence and the frozen task versions, never later live inputs. Unlock makes old T-09/T-10 historical and invalidates T-04 currentness; it does not delete any historical attestation. Per-task blockers never replace the hard guard register of §6.

## 9. Business dates and close history (DEC-022)
Business day = Monday–Friday excluding the project's explicit holiday dates. No internet holiday lookup, locale-dependent weekend or background scheduling. Configuration: close.start_business_day 1..60 default 1; close.target_lock_business_day 1..60 default 5 (must be ≥ start); close.holidays sorted unique Gregorian dates, 0..1000, default []. Tasks have signed offset -60..60 business days from period end. Positive n counts n eligible dates strictly AFTER period end; negative n counts before it; zero is period end if eligible, otherwise the first eligible date after it. Weekend holidays are legal and do not double-count. Do not clip unrepresentable dates: fail the enclosing start-close/task edit with ERR-002 before any write. No change to fiscal year identity or frozen calendar product code in M0.

Calendar/template changes affect only later start-close instantiations (including existing open periods not yet started), not closing/locked periods. Default task offsets are initial values, not auto-adjusted after a live edit. Template T-09/T-10 offsets must track target lock day atomically. The close-template endpoint is the sole writer for these three close settings and template entries; generic settings PUT rejects these keys (ERR-105). They have one storage owner, not two independently mutable copies. Period copies include holiday dates and offsets so future template/holiday changes cannot rewrite history.

Overdue = evaluated_on > due_date AND effective status not in done/waived. evaluated_on comes from the injected server UTC civil date; API returns it, the UI must not silently substitute the browser timezone. On the due date itself the task is not overdue; alerts become eligible on the next civil day per §3. This is display/escalation, not a close permission. The calendar has a preview for never-started periods, explicitly instantiated=false and using the current template; tasks remain absent and readiness false. Annual planning milestones in doc 48 are a separate category and do not become close prerequisites through this API.

Hand-worked date oracles: period end Fri 2026-01-30, holiday Mon 2026-02-02 → offsets 0=Jan30, +1=Feb03, +5=Feb09, -1=Jan29. End Sat 2026-01-31 → 0=Feb03 and +1=Feb03; -1=Jan30. Leap end Thu 2028-02-29 → +1=Mar01. End Fri 9999-12-31 +1 is unrepresentable, not 9999-12-31 again. May 2026 month-2 starts after Apr30: +1=May01, +5=May07 with no holidays.

Close history reads CLOSE_SIGNOFF, PERIOD_LOCK and RESTATE_OPEN in durable audit_id order, not wall-clock order; retained records remain accessible after unlock/new sign-off. A history record never carries current authorisation. Legacy events lacking full retained bindings are explicitly labelled legacy with record=null, never fabricated approvals. A missing record for a new-format event is corruption (ERR-099), not legacy. No arbitrary audit JSON or actor credential is exposed by this bounded history DTO. Actual snapshot/invalidation persistence still needs the WI-0001 follow-through already recorded for DEC-021.
