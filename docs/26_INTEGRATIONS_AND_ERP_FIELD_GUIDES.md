# 26 — INTEGRATIONS & ERP EXPORT FIELD GUIDES

> v1 integration = **files, done perfectly** (no live connectors — PRD 01 §4). This doc makes "any ERP" concrete so import is never a guessing game. **Dynamics 365 is the first-class source** (DEC-012: the owner's own ledger lives there): the F&O and Business Central export shapes below are the ones the sample corpus ships in (`sample-data/erp_shapes/`, doc 42 §4), the import wizard recognises them from their headers, and the rectification journal (§7) writes back in their journal-import shapes. Every other ERP goes through the same presets-as-data mechanism.

## 1. Canonical import templates (ship as downloadable .xlsx/.csv from S03)
GL template: Entity, Account, CostCentre, Vendor, VoucherNo, DocDate, PostingDate, Description, Debit, Credit (or signed Amount). Budget: Period, Entity, Account, CostCentre, Amount. Drivers: Period, Entity, Driver, Account(optional), Value. Opening: Account, Entity, Amount(signed). Subledger (bank/AR/AP/payroll): Date, Reference, Party, Amount(signed), Account(optional). Each template has an instruction row + 3 example rows + a "do not rename headers in your saved mapping" note.

## 2. Per-ERP export recipes (step lists in S15/doc 18 appendix; mapping profile presets shipped)
- **Microsoft Dynamics 365 Finance / F&O** — *General ledger → Inquiries and reports → Voucher transactions* (filter: date range = the period, all journals) → **Export to Excel**; the vendor comes from a second export, *Accounts payable → Inquiries → Vendor transactions* for the same dates (vendor enrichment, §5); monthly tie-out from *Trial balance* (same date range, same posting layer); budgets from *Budgeting → Budget register entries* (lines export) or the budget-plan Excel template. Presets `D365FO-GL v1`, `D365FO-AP v1`, `D365FO-TB v1`, `D365FO-Budget v1`. Posting layers outside the project's scope (default `Current` only) are quarantined, never mixed in (§5).
- **Microsoft Dynamics 365 Business Central** — *General Ledger Entries* page (filter Posting Date to the period) → **Open in Excel / Share → Export to Excel**; vendor = `Source No.` when `Source Type` = `Vendor`; budgets from *G/L Budget Entries*; trial balance from *Trial Balance* report (Excel layout). Presets `D365BC-GL v1`, `D365BC-Budget v1`, `D365BC-TB v1`.
- **Tally (India)** — Day Book / Ledger exports via XML→CSV guidance + Tally ODBC note; parentheses negatives; preset `Tally-GL v1`.
- **SAP (ECC/S4)** — FBL3N/FAGLL03 layouts; leading-zero account handling (text, never numeric-strip); preset `SAP-GL v1`.
- **QuickBooks / Xero / Zoho Books** — Journal/General Ledger reports; date-format presets (MM/DD vs DD/MM declared, never guessed — doc 06 ambiguous-date quarantine); presets per product.
- **Generic/legacy** — profiler + suggestions carry the load; analyst saves as a named profile (month-2 free).
Presets are *mapping profiles as data* — adding one needs no code release.

## 3. Future connectors (Phase 2, contract-first)
When built, connectors must land data through the identical staging→validation→commit pipeline (a connector is just another file producer writing import_batches) — no connector may write gl_rows directly. API credentials, if ever, live in OS keyring only. This constraint is architectural (doc 04) so Phase 2 cannot bypass quarantine/TB/audit.

## 4. Export integrations
Excel/PPT/PDF (docs 09/10); owner action list (Excel per owner, S08); **rectification journal** (§7); diagnostics bundle (12 §5); CSV re-export of any table grid (same formula-injection guard). No email sending in v1 (no stored SMTP credentials) — files are shared by the analyst's normal tools.

## 7. Write-back formats — the rectification journal (doc 07 §7; `app/exports/journal_export.py`)
The app **never posts** to an ERP. It writes a journal file the accountant imports into the ERP's journal screen, reviews, and posts. One export = one period's queued suggestion lines (`findings.suggestion_status = queued`, optionally filtered by finding ids), one file, one `reports` row with sha256; the findings move to `corrected` with the report id. Formats (`format` parameter of `POST /projects/{id}/exports {kind: journal}`):
- **`d365fo_general_journal`** (.xlsx, one sheet `Lines`, header row = the General journal data-entity field names so the file opens in *Data management → Import* or the journal's *Open lines in Excel* after column matching; default template — confirm once against your environment's entity template and adjust the write-back profile in S13): `JOURNALBATCHNUMBER` (blank — assigned by F&O), `LINENUMBER`, `TRANSDATE` (ISO), `ACCOUNTTYPE` = `Ledger`, `ACCOUNTDISPLAYVALUE` (built from `erp.d365fo.ledger_account_format`, default `{main_account}-{entity}-{cost_centre}`; for reversing/credit legs of an existing row the stored `source_account_ref` is written verbatim), `DEBITAMOUNT`, `CREDITAMOUNT` (decimal strings, 2 dp), `TEXT` (description incl. the `[FPA EXC-### <voucher>]` tag, ≤ 60 chars after truncation at a word boundary — the full text goes to the `Readable` sheet), `CURRENCYCODE`, `OFFSETACCOUNTTYPE`/`OFFSETACCOUNTDISPLAYVALUE` (blank — lines are written one-sided and balanced per voucher; F&O validates balance on posting), `DOCUMENT` = the finding key, `DOCUMENTDATE`. A second sheet `Readable` lists the same lines with labels, the finding, the basis sentence and the confidence — for the reviewer.
- **`d365bc_general_journal`** (.xlsx, header row = BC General Journal *Edit in Excel* columns): `Posting Date`, `Document Type` (blank), `Document No.` (finding key, ≤ 20 chars → `FPA-<finding_id[:12]>`; the full key sits in `Description`), `Account Type` = `G/L Account`, `Account No.`, `Description`, `Debit Amount`, `Credit Amount`, `Shortcut Dimension 1 Code`, `Shortcut Dimension 2 Code`, `Bal. Account Type`/`Bal. Account No.` (blank), `External Document No.` (original voucher).
- **`generic_csv`**: `date, entity, account, cost_centre, debit, credit, description, reference, finding_key, suggestion_kind, confidence` — UTF-8 with BOM, formula-injection guard on text (doc 09 §5).
Invariants (tested): the file nets to zero per finding and in total; amounts are decimal strings from money.py (never floats); row order = finding key, then line order; re-export of the same queue is byte-identical except the timestamp cell on `Readable`; a queue with zero lines → ERR-046 (nothing to export), never an empty file.

## 5. Preset mapping tables (normative — presets ship as data; analysts can override per project)
Columns: Canonical (doc 06) ← source headers (case-insensitive, trimmed). Confidence = deterministic suggester's expected top-1 basis.

### D365FO-GL v1 (Dynamics 365 Finance / F&O — *Voucher transactions* inquiry, Export to Excel)
Typical headers (names vary by version and personalisation; the saved profile absorbs the variation once): `Journal number`, `Voucher`, `Date`, `Ledger account` (segmented string in the account-structure order, e.g. `601200-IN01-022-`), `Account name`, `Description`, `Currency`, `Amount in transaction currency`, `Amount` (accounting currency, signed), `Debit`, `Credit`, `Posting type`, `Posting layer`, `Created by`, `Created date and time`.
entity ← **constant** (the legal entity you were in when exporting — F&O exports are per legal entity; a `Company`/`DataAreaId` column, when present, overrides) · account ← `Ledger account` segment 1 (transform `split:ledger_account:1`; the profile declares the segment order once, e.g. `[main_account, business_unit, cost_centre, department]`, and the raw string is kept in `gl_rows.source_account_ref` so the rectification export can address it verbatim) · cost_centre ← the segment declared as cost centre (`split:ledger_account:3` in the example) · voucher_no ← `Voucher` (**not** journal number — one journal holds many vouchers; the journal number is kept in the description tail `[JNL <no>]` only if the analyst ticks it) · posting_date ← `Date` (ISO in Excel exports; declared) · document_date ← `Document date` when exported, else = posting_date (recorded in the profile) · description ← `Description` (fallback `Transaction text`) · amount ← `Amount` signed, or `Debit`/`Credit` pair when `Amount` is absent (never both mapped — ERR-022) · fx_currency/fx_amount ← `Currency` / `Amount in transaction currency` · posted_by ← `Created by` · posted_at ← `Created date and time` · posting_layer ← `Posting layer`: rows whose layer ∉ `import.posting_layers` (default `Current`) are quarantined `OUT_OF_SCOPE_LAYER` (so a Tax- or Custom-layer re-measurement never lands in the management ledger unnoticed; the analyst can widen the setting per project) · vendor ← **empty** (this inquiry carries no vendor; names are never parsed out of descriptions) — filled by `D365FO-AP v1` enrichment below.
### D365FO-AP v1 (*Vendor transactions* inquiry — AP sub-ledger for vendor enrichment and reconciliation)
Headers: `Vendor account`, `Name`, `Voucher`, `Date`, `Invoice`, `Amount`, `Currency`, `Transaction type`, `Due date`, `Description`. Imported as `source_kind=subledger`, `subledger_kind=ap`. **Enrichment** (doc 06 §2 step 9): after commit, GL rows of the same entity and period whose `(voucher_no, posting_date)` match exactly one AP row receive `vendor_id` (`vendor_source = ap_match`); many-to-one matches are reported, never guessed; unmatched counts shown. The same batch feeds the AP reconciliation (doc 19 §I).
### D365FO-TB v1 (*Trial balance* inquiry export — per-account tie-out)
Headers: `Ledger account`, `Name`, `Opening balance`, `Debit`, `Credit`, `Net difference`/`Closing balance`. Imported as `source_kind=tb_check` for a period: per account, `Debit − Credit` (or `Net difference`) is compared with Σ committed `gl_rows.amount_minor`; any non-zero difference is listed by account with the ERP and app figures; the period's close checklist item "TB tie-out" (doc 30) is green only at zero differences. The same file can be attached to a staged GL batch as **per-account control totals** (doc 06 §2 step 6): mismatches block commit with ERR-023 details by account.
### D365FO-Budget v1 (*Budget register entries* lines export / budget plan Excel)
Headers: `Budget model`, `Date`, `Ledger account`/`Ledger dimension` (same segmented string → same split transform), `Amount`, `Amount type` (Expense/Revenue → sign convention), `Currency`. Period ← `Date`; version ← `Budget model` (e.g. `Original`, `Revised`).
### D365BC-GL v1 (Business Central — *General Ledger Entries* page, Open in Excel)
Headers: `Entry No.`, `Posting Date`, `Document Type`, `Document No.`, `G/L Account No.`, `G/L Account Name`, `Description`, `Amount`, `Debit Amount`, `Credit Amount`, `Global Dimension 1 Code`, `Global Dimension 2 Code`, `Source Code`, `Source Type`, `Source No.`, `User ID`, `External Document No.`, `Document Date`.
entity ← constant (company of the export) · account ← `G/L Account No.` (`keep_text`) · cost_centre ← the global dimension the profile designates (default `Global Dimension 1 Code`) · voucher_no ← `Document No.` · posting_date ← `Posting Date` · document_date ← `Document Date` when present · description ← `Description` · amount ← `Amount` signed (or Debit/Credit pair) · vendor ← `Source No.` **only when** `Source Type` = `Vendor` (transform `conditional:Source Type=Vendor`), else empty · posted_by ← `User ID` · reference ← `External Document No.` (kept in evidence for EXC-028 — same external document number on two vouchers is quoted in the finding).
### D365BC-Budget v1 / D365BC-TB v1
Budget: `Budget Name` (→ version), `Date`, `G/L Account No.`, `Global Dimension 1/2 Code`, `Amount`. TB: `No.`, `Name`, `Net Change` (or `Debit Amount`/`Credit Amount`), `Balance` → same per-account tie-out as `D365FO-TB v1`.
### Tally-GL v1 (TallyPrime Ledger/Day-Book CSV via export)
entity ← Company (export is per-company; constant transform) · account ← Ledger · cost_centre ← Cost Centre (if enabled) · voucher_no ← Voucher No. · posting_date ← Date (DD-MM-YYYY declared) · description ← Narration (hostile-data rules) · amount ← Amount signed; if Dr/Cr suffix present (`1,200 Dr`) the transform `tally_dr_cr` converts suffix to sign — suffix parsing is part of this preset's tests.
### SAP-GL v1 (FAGLL03/FBL3N)
entity ← Company Code · account ← Account (leading zeros preserved: transform `keep_text`) · cost_centre ← Cost Center · voucher_no ← Document Number · posting_date ← Posting Date (declared format) · document_date ← Document Date · description ← Text · debit ← Debit (local curr.) · credit ← Credit (local curr.) · vendor ← Vendor where present.
### QuickBooks-GL v1 / Xero-GL v1 / Zoho-GL v1
entity ← constant (single-company exports) · account ← Account · voucher_no ← Num / Journal # / Transaction ID resp. · dates declared per preset (QB: MM/DD/YYYY; Xero/Zoho: DD/MM/YYYY default but profile records the analyst's confirmation — doc 06 ambiguous-date quarantine still applies) · amount ← Amount signed (QB/Xero) or Debit/Credit pair (Zoho).
### Legacy alias
`D365-GL v1` (pre-DEC-012 name) resolves to `D365FO-GL v1`; saved profiles created under the old name keep working.

## 6. Preset governance
A preset change is a data PR with: sample file (synthetic), expected mapping result, changelog (docs/CHANGELOG). Wrong-preset reports are S2 defects (doc 72). New ERP presets are the cheapest "integration" we ship — support can author one from a client sample in under a day using this section's pattern.
